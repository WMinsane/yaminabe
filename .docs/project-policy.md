# プロジェクト方針書（骨子）

> リリースすることより、無駄なく、品質を高め、計画と計測の可視化を徹底する。

---

## 1. 基本理念

### 目指すもの
- **計画駆動**: 場当たり的な指示・対応を排し、全体像を見据えた上で行動する
- **可視化**: 計画・進捗・品質・振り返りのすべてを記録し、フェーズ毎に評価・改善する
- **品質優先**: リリース速度より、手戻りの少ない堅実な開発を優先する
- **認識齟齬の排除**: ラリー（やり取りの往復）を最小化し、1回の指示で正しく動ける仕組みを作る

### mmkプロジェクトからの継承

| 継承（良かった点） | 改善（反省点） |
|---|---|
| `.issue/` `.investigation/` による課題の起票→解決サイクル | 場当たり的な指示による手戻りの多発 |
| Severity/Statusの明確な定義 | AIが計画なしに実装に突入 |
| `/custom-close` による課題完了→ドキュメント更新の連動 | 認識齟齬（定数 vs 環境変数、ドキュメント配置ミス等） |
| `.user-eval/` による振り返り・自己評価 | 完了条件が曖昧なまま着手 |
| エスカレーションルール（変更→即ドキュメント反映） | 事前調査不足でのAPI仕様齟齬 |
| アセット配置チェック（hook）による構造強制 | ドキュメントの関心分離違反 |

## 2. AI協業ルール

### 実行前の義務（ラリー最小化のため）
1. **計画提示**: 実装前に番号付き計画を提示し、承認を得る
2. **完了条件**: 何をもって「完了」とするか明文化してから着手
3. **影響範囲**: 変更対象ファイル一覧を事前に提示
4. **削除・上書きの説明**: 既存コードやファイルの削除・上書き時は変更内容を説明

### 禁止事項
- 承認なしの実装着手
- 過剰な抽象化・将来のための先行実装
- ドキュメントの関心分離違反（アーキテクチャ情報をspec.mdに混入する等）
- 定数と環境変数の混同
- 未使用コードのコミット

## 5. 課題管理ルール（mmkから継承・強化）

### ディレクトリ構成
```
.issue/          → バグ・機能不足・技術的負債
.investigation/  → 調査タスク（API仕様調査、技術検証等）
.user-eval/      → 開発プロセス振り返り・評価
```

### 命名規則
`{連番3桁}_{スネークケース概要}.md`

### 必須ヘッダ
```markdown
# {番号}: {タイトル}

**Type**: issue / investigation
**Status**: Open / In Progress / Closed
**Severity**: Critical / High / Medium / Low
**完了条件**: （着手前に必ず記載）
```

### Severity定義
| レベル | 基準 |
|---|---|
| Critical | コア機能の破壊・データ損失 |
| High | 機能が著しく制限される |
| Medium | 動作するが改善が必要 |
| Low | 軽微・改善提案 |

### 強化ポイント（mmkからの改善）
- **完了条件を着手前に必ず記載**する（mmkでは曖昧なまま着手することがあった）
- 課題完了時はドキュメントへのエスカレーション要否を必ず確認

## 6. 計測・可視化

### 6.1 目的
「初期ドキュメントから一発で成果物を得る」を理想とし、乖離を定量把握・改善する。

### 6.2 計測観点（5軸・全フェーズ共通）

| # | 観点 | 指標 | 分母 | データソース |
|---|---|---|---|---|
| 1 | ラリー数 | ユーザー→AIのやり取り回数 | 成果物のコード全量（行数） | セッションJSONL |
| 2 | 指示分量 | ユーザーメッセージの合計文字数 | 成果物のコード全量（行数） | セッションJSONL |
| 3 | 手戻り率 | (変更行数 + 削除行数) / 新規行数 | — | セッションJSONL（Edit/Write結果） |
| 4 | 手戻り原因分類 | ユーザー起因 / Claude起因 の割合 | 手戻り総件数 | セッションJSONL（reject/interrupt/方針転換） |
| 5 | トークン効率 | 生成行数（コード+ドキュメント）/ トークン消費量 | — | セッションJSONL |

**ラリー数と指示分量の関係**: 両指標は重複する部分があるが、併用することで定性的な分析に役立つ。例：ラリー数が少なくても指示分量が多い場合は「1回の指示が冗長」であり、ラリー数が多くても指示分量が少ない場合は「認識齟齬による細かい軌道修正が頻発」していることを示す。

### 6.3 フェーズとタグ
- 指標は全フェーズ共通。フェーズタグを記録に付与し、事後分析で特性差を明らかにする
- フェーズ名は§7.1のフェーズ定義に準ずる（方針・仕様策定 / スケジュール策定 / Git運用策定 / ドキュメント整備 / モック開発 / UI改善 / 開発（初回RUN）/ フィードバックと修正 / テスト仕様書作成 / テスト実施 / バグ修正・仕様書メンテ）
- 目標数値は初回フェーズ完了後に実データから設定する

### 6.4 集計タイミング
- **フェーズ終了時**: カスタムコマンドでセッションJSONLを一括解析しレポート出力
- セッションJSONLに全記録が残るため、リアルタイム集計は不要

### 6.5 手戻りの検出基準

Edit/Writeツールで編集または削除が発生した時点で手戻りとしてカウントする。

**原因分類**（検出より重要）:

| 区分 | 判定基準 | 例 |
|---|---|---|
| ユーザー起因 | ユーザーの指示変更・追加要件・方針転換 | 「やっぱりこうして」「観点が抜けていた」 |
| Claude起因 | ドキュメント見落とし・判断ミス・指示の誤解 | reject後の再実行、方針書と矛盾する実装 |

### 6.6 トークン節約施策
- CLAUDE.mdは500行以内を維持。専門ワークフローはスキルに移動
- 調査・探索はサブエージェントに委任（メインコンテキストを圧迫しない）
- テスト等の冗長出力はhookでフィルタリング

## 7. フェーズ定義とコンテキスト管理

### 7.1 開発初期フェーズ

| # | フェーズ | 内容 | コンテキスト操作 |
|---|---|---|---|
| 1 | 方針・仕様策定 | 本方針書・アプリ仕様・セキュリティ方針 | — |
| 2 | スケジュール策定 | フェーズ別のマイルストーン定義 | `/compact` |
| 3 | Git運用策定 | ブランチ戦略・コミット規約 | `/compact` |
| 4 | ドキュメント整備 | CONVENTIONS.md等の残ドキュメント作成 | `/compact` |
| 5 | モック開発 | ブランチ切り分け、UIモック作成 | `/clear`（実装開始のため文脈断絶） |
| 6 | UI改善 | モックへのフィードバック反映 | `/compact` |
| 7 | 開発（初回RUN） | 仕様+モックを元に実装。やり取りなし | `/clear`（新規実装のため） |
| 8 | フィードバックと修正 | 初回RUN結果に対するやり取り・修正 | `/compact` |
| 9 | テスト仕様書作成 | テストケース・境界条件・エラーシナリオの定義 | `/clear`（実装→テストの断絶） |
| 10 | テスト実施 | テスト仕様書に基づく実行 | `/compact` |
| 11 | バグ修正・仕様書メンテ | バグ修正と仕様書更新を交互に実施。1フェーズとして扱う | `/compact` |

- `/clear`: 文脈の断絶が大きいフェーズ間（ドキュメント→実装等）で使用
- `/compact`: 連続性のあるフェーズ間で使用

### 7.2 コンテキスト運用ルール

- 第三者ツール（claude-mem等）は不使用。組み込み機能で対応
- 永続すべき情報: CLAUDE.md / memory/ に記載（会話履歴に依存しない）
- MCP: 未使用サーバーは無効化し、ツール定義によるコンテキスト消費を防ぐ
