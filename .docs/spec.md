# アプリ仕様書

## コンセプト

エコーチェンバーと成長を阻むネット環境からの脱却。
パーソナライズとランダム性を両立し、「何が出てくるかわからない」体験を通じて視野拡大・自己成長・情報収集を兼ねる。

## F-01: フィード表示

### 概要

日次バッチで収集済みのコンテンツプールから、ユーザーの条件に合致する記事を取得・表示する。
収集処理の詳細は「コンテンツ収集」セクションを参照。

### フィード取得フロー（Server Component）

```
1. 条件（カテゴリ + 配信モード）に合致する記事をDBから取得
2. 有料ユーザー: タグweight（優先）→ カテゴリweight → 配信モードの順でスコアリング
3. 無料ユーザー: カテゴリ + 配信モードのみでフィルタリング（weight適用なし）
```

### フィードアイテムの表示情報

| 項目 | 説明 |
|------|------|
| タイトル | 記事タイトル |
| ソース | 配信元（はてブ / note / ブログ名等） |
| カテゴリ | 記事のカテゴリ（階層表示） |
| サマリ | 記事の要約（取得可能な場合） |
| ブックマーク数 | はてブの場合、ブックマーク数を表示 |
| 公開日 | 記事の公開日時 |
| Newバッジ | 今回バッチで初めて登録された記事に表示（content.collected_at = 当日バッチ日時） |

## F-02: フィード条件変更

### 仕様

条件変更時はサーバーから再取得する。無料ユーザーは条件変更に回数制限あり。

| プラン | 条件変更 | 制限方式 |
|--------|---------|----------|
| 無料（アカウントなし） | 1日1回 | cookie（有効期限: 24時間） |
| 有料（アカウントあり） | 自由 | 制限なし |

- 無料ユーザーが条件変更済みの場合、UIで「次回変更可能: 23:30以降」を表示（日次バッチ直前にリセット）
- cookie期限切れ・クリアで再変更可能（厳密な制御は行わない）
- カテゴリ・配信モードを変えても同一記事が含まれることがある
- 未認証リクエストに対しIPベースのレートリミット（API層）で過剰アクセスを防止（認証済みユーザーは対象外）

## F-03: ユーザーアクション

### 概要

ユーザーと記事の組み合わせで1レコード（user_action）。各アクションはbooleanフラグで管理。

| フラグ | トリガー | UI | パーソナライズへの影響 |
|--------|---------|-----|---------------------|
| is_clicked | リンクタップ | — | ポジティブ（該当カテゴリの重み増加） |
| is_bounced | クリック後に早期帰還 | — | ネガティブ（記事は好みでなかった） |
| is_bookmarked | ブックマークボタン（トグル） | ブックマークアイコン | 強ポジティブ |

- アクションなし（user_actionレコードなし）= 興味なしとして扱う（JOINで判定）
- ブックマーク済み記事はライブラリ画面（S-02）のブックマークタブで閲覧（ソート: bookmarked_at 降順）

### デバウンス方式

トグル操作のいたずら防止・二重カウント防止のため、クライアント側でデバウンスを行う。

1. UIは楽観的に即時反映（タップ直後にアイコン切替）
2. 最後の操作から一定時間（500ms〜1s）経過後に最終状態を送信
3. サーバー側はbooleanフラグのupsert（べき等操作、二重カウント問題なし）
4. 高速トグル中の中間状態は送信しない

### 保存先

有料ユーザー（アカウントあり）のみ。サーバーDB（user_action）に永続化し、パーソナライズに活用。

## F-06: 配信モード選択

### 仕様

| モード | コード値 | 説明 |
|--------|---------|------|
| トレンド | trend | 人気・話題の記事を中心に配信 |
| ディープ | deep | 専門性の高い記事を中心に配信 |

## F-07: カテゴリ設定

### カテゴリ体系

親子階層構造。categoryテーブルのparent_idで管理。

```
ビジネス（大分類）
├── 経済
├── テクノロジー
│   ├── AI・機械学習
│   └── Web開発
├── マーケティング
└── ...

社会（大分類）
├── 政治
├── 国際
└── ...

暮らし（大分類）
├── 健康
├── 料理
└── ...
```

- 初期データはシステム稼働前に投入（マスタデータ）
- ユーザーはいつでもカテゴリを追加・削除可能

### 配信比率の設計

**カテゴリweight:**
- 大分類間は均等配分（偏りを防止）
- 大分類内の子カテゴリはデフォルト均等割り
- 子カテゴリ未選択の大分類は、大分類全体として配信（子カテゴリ指定なし）
- IPW（逆傾向スコア重み付け）により日次でweight更新（有料ユーザーのみ）
- weight範囲: 0.2〜0.5（マイルドな調整、極端な偏りを防止）

**タグweight（カテゴリより優先）:**
- タグはシステムが自動付与（ソース側メタデータ優先、なければタイトル・要約から自動抽出）
- ユーザーの行動記録（クリック/バウンス/ブックマーク）からタグweightをIPWで日次調整
- カテゴリより粒度が高く、ユーザーの性向をより正確に反映する
- weight範囲: カテゴリと同様 0.2〜0.5

**スコアリング優先順位:**
タグweight > カテゴリweight > 配信モード

## F-09: アカウント管理

### 概要

無料ユーザーはアカウント不要で利用可能。有料機能（履歴・データ永続化）を利用するにはアカウント登録が必要。

### 認証方式

- NextAuth（Auth.js）+ Prisma Adapter + Credentials Provider
- メールアドレス + パスワード認証
- セッション管理: DBセッション方式（sessionテーブルで管理、サーバー側で即時無効化可能）
- OAuth（Google / Apple）は将来対応として併存可能な設計とする

### パスワードリセットフロー

1. 認証画面（S-05）で「パスワードを忘れた」リンク押下
2. メールアドレス入力 → verification_tokenテーブルにトークン生成（有効期限: 10分）
3. Resendでリセットリンクをメール送信
4. リンク押下 → トークン検証（期限切れ・使用済みチェック）
5. 検証OK → パスワード変更画面（S-06）へ遷移
6. 新パスワード + パスワード（確認）を入力
7. 変更完了 → 認証画面（S-05）へリダイレクト

### メール送信基盤

- Resend（月3,000通無料枠、MVP期間中は十分）
- パスワードリセットメールのみ（MVP時点）

### クロスプラットフォーム（将来対応）

- Web版でMVP完成後にReact Native（Expo）で展開
- 同一アカウントでWeb版・アプリ版にログイン
- ブックマーク・設定・履歴はすべてサーバー同期

## コンテンツ収集

### 収集タイミング（Python別プロセス）

- 日次バッチ: 1日1回（収集・タグ付与・配信バッチ生成・weight更新を一括処理）
- 全カテゴリ × 全配信モードでRSS/APIを巡回し、content登録 + delivery_batch/delivery_batch_item生成
- 収集記事にタグ付与（ソース側メタデータ優先、なければタイトル・要約から自動抽出）
- 有料ユーザーのIPW評価 → タグweight・カテゴリweight更新（ユーザー性向反映）
- URL重複時は先勝ち（既存レコードがあればスキップ）

### ソース別仕様

#### はてなブックマーク（第1優先）

| エンドポイント | 用途 |
|---------------|------|
| `https://b.hatena.ne.jp/hotentry/{category}.rss` | カテゴリ別ホットエントリ |
| `https://b.hatena.ne.jp/entrylist/{category}.rss` | カテゴリ別新着エントリ |
| `https://b.hatena.ne.jp/entry/jsonlite/?url={url}` | 個別記事のブックマーク情報 |

**はてブカテゴリ:**
`all` / `general` / `social` / `economics` / `life` / `knowledge` / `it` / `entertainment` / `game` / `fun`

#### RSSフィード（第2優先）

- note: `https://note.com/{creator}/rss`
- 個人ブログ・ニュースサイト: 各サイトのRSS/Atomフィード

#### Web検索結果（第3優先・将来）

- Google Custom Search API
- 実装は後回し

### 重複排除

- 記事URLで一意制約（content.url）
- 同一URLが複数ソースから取得された場合、先勝ち（既存レコードがあればスキップ）

## データ取得・処理方式

API Route（route.ts）は作成しない。全処理をServer Components / Server Actions / 外部バッチで実装する。

### Server Components（データ取得・画面描画）

Server Componentで直接DBアクセス。認証状態はNextAuthのセッションで判定。

- フィード取得（条件はcookie/URLパラメータから取得。認証不問）
- カテゴリ一覧（階層構造。認証不問）
- アクティビティ履歴一覧（有料・認証必須）
- ユーザー設定取得（有料・認証必須）
- 週次ランキング取得（有料・認証必須）
- 記事に対するユーザーアクション取得（有料・認証必須）

### Server Actions（ミューテーション処理）

- 行動記録（クリック/バウンス/ブックマーク/メモ）— 有料・認証必須
- ユーザー設定更新（配信モード等）— 有料・認証必須
- ユーザーカテゴリ設定更新 — 有料・認証必須
- パスワードリセット申請（メール送信）— 認証不問
- パスワード変更（トークン検証 + 新パスワード）— 認証不問

### 認証（NextAuth）

NextAuth（Auth.js）が自動的にRoute Handlerを生成。個別のAPI Route定義は不要。

### 日次バッチ（Python別プロセス）

Next.jsとは独立したPythonスクリプトとして実装。

- コンテンツ収集（RSS/APIクロール → content登録 + delivery_batch/delivery_batch_item生成）
- タグ付与（ソース側メタデータ優先、なければタイトル・要約から自動抽出）
- 有料ユーザーのIPW評価 → タグweight・カテゴリweight更新
